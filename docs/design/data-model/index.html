제품 공정조건은 어떻게 저장되는가

현재 구현의 물리 테이블과 논리 참조를 함께 살펴보는 ERD입니다. 화면에서는 ‘제품’으로 부르되 내부 모델은 Project를 유지합니다. 표를 누르면 전체 컬럼·NULL 허용·키·제약을 확인할 수 있습니다.

앱 DB 13개 테이블 · ORM 151개 컬럼 · 마이그레이션 0001–0008 대조 · 실행 중인 DB의 스키마를 직접 조회한 결과는 아닙니다.

식별: LINE · Process · Part ID

별도 product 테이블은 없습니다. 이 조합과 상태·버전을 project가 보관합니다.

조건표: Layer → 조건 행 → 셀

셀은 parameter_code와 텍스트 값으로 저장하며 정의와는 논리적으로 연결됩니다.

리비전: project 행을 새로 생성

동일 조합의 과거 버전은 archived로 남고 새 초안에 조건표를 복사합니다.

현재 저장 규칙

  • 승인된 원본에서 리비전을 만들면 원본은 archived, 복사본은 draft가 됩니다.
  • Profile·Layer·조건 행·셀을 새 버전으로 복사합니다. 이력·댓글을 그대로 복제한다는 뜻은 아닙니다.
  • revision_of_id는 직전 버전, revision_root_id는 최초 버전을 가리킵니다.
  • 같은 root 안에서 version은 유일하고, 직전 버전 하나에 직접 후속 버전은 최대 하나입니다.

합의된 UI 규칙 ≠ 현재 목록 API

‘조합별 최신 버전만 표시, LINE별 25건’은 합의된 개선안입니다. 현재 목록 API에는 최신 리비전만 선택하는 필터가 없습니다.

실제 구현 시 서버에서 최신 선택·LINE·검색 조건을 적용한 뒤 페이지를 나눠야 합니다. 최신은 ‘최신 승인본’과 다릅니다.

별도 테이블로 오해하지 않기

  • Backbone: sheet_layer.backbone_snapshot JSONB와 출처 식별자에 보관합니다.
  • 사용자: actor·author·locked_by 문자열입니다. User 테이블은 없습니다.
  • 검증 결과: 계산 결과이며 ValidationResult 테이블은 없습니다. 규칙은 validation_rule에 저장합니다.
  • 승인 근거: project의 snapshot·review_basis_hash·review_rule_versions에 보관합니다.
  • 제품명: 사용자 화면에서는 사용하지 않기로 했지만 project.name은 현재 필수 컬럼으로 남아 있습니다.

모델과 마이그레이션의 차이

현재 ORM 선언과 0008까지의 마이그레이션을 비교했습니다. 아래 차이가 실제 운영 DB에도 존재하는지는 별도 스키마 확인이 필요합니다. 이번 산출물은 스키마를 수정하지 않습니다.

전체 테이블·필드 찾아보기

컬럼 타입·NULL·enum은 ORM 선언 기준입니다. DB에 적용된 제약의 차이는 위 표를 함께 확인하세요. 관계선을 따라가지 않아도 모든 정보를 읽을 수 있습니다.

검토할 핵심 제약

  • LINE + Process + Part ID는 status ≠ archived인 행에만 유일합니다. 과거 버전은 공존합니다.
  • Project Profile은 앱에서는 1:1을 기대하지만, DB PK/FK는 프로젝트당 최대 1개만 보장합니다.
  • Layer마다 POR 조건은 부분 유일 인덱스로 최대 1개이며, 항상 1개 존재함을 DB가 보장하지는 않습니다.
  • 셀은 (condition_id, parameter_code)가 유일합니다. parameter_code에는 FK가 없습니다.
  • 댓글의 condition/layer/parameter는 모두 NULL이거나 모두 존재해야 합니다. 셀 대상 좌표에는 FK가 없습니다.
  • 리비전 self-FK는 ON DELETE SET NULL이지만 v>1 계보 CHECK와 충돌할 수 있으므로 과거 버전을 자유롭게 삭제할 수 있다는 뜻이 아닙니다.
