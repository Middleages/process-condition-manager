## 1. 프로젝트 개요

### 1.1 배경 및 문제

반도체 Photo 공정에서 공정조건표는 제품 생산의 핵심 데이터이다. 현재 이 데이터는 Excel과 사내 전산 시스템을 혼용하여 관리되고 있으며, 다음과 같은 문제가 있다.

- **데이터 규모**: 제품당 약 300개의 조건 파라미터(컬럼) × 30~60개 레이어(행)로, 사람이 직접 관리하기에 극도로 어려운 크기
- **복잡한 초기 데이터 구성**: 신규 제품 조건표 작성 시 기존 제품(backbone)에서 복사 후, 레이어별로 서로 다른 backbone을 조합하는 작업이 수작업으로 이루어짐
- **최신화 어려움**: 양산 중 변경된 설비 Recipe가 조건표에 반영되지 않아 데이터가 실제 현장과 불일치
- **오기입 위험**: 수백 개의 셀을 수작업으로 편집하므로 범위 초과, 필수값 누락, 논리적 모순 등의 오류 발생 빈도가 높음
- **전산 입력 부담**: 완성된 조건표를 약 10개의 사내 전산 시스템에 각각 포맷에 맞게 복사·붙여넣기로 입력해야 함

### 1.2 목표

웹 기반 공정조건표 관리 시스템을 구축하여 다음을 달성한다.

1. Backbone 기반 조건표 초안 생성과 레이어별 조합을 체계화
2. 설비 Recipe XML 파싱을 통한 자동 최신화 지원
3. 300개 컬럼을 카테고리별로 나누어 편집 가능한 사용자 친화적 UI 제공
4. 실시간 검증과 backbone 대비 변경 추적으로 오기입 방지
5. 전산 시스템별 포맷에 맞는 출력 테이블 자동 생성

### 1.3 사용자

| 역할 | 인원 | 권한 |
|------|------|------|
| **편집자** | ~15명 | 조건표 생성, 편집, 저장, 검토 요청 |
| **검토자** | ~5명 | 조건표 열람, 승인, 반려(코멘트) |
| **관리자** | 1~2명 | 시스템 설정 전체, 사용자 역할 지정 |

### 1.4 시스템 형태

독립 웹 애플리케이션으로 구축한다 (기존 Cloud Portal과는 별도 운영).

## 3. 데이터 구조

### 3.1 공정조건표 구조

| 구분 | 설명 |
|------|------|
| **행(Row)** | 레이어 (Layer). 제품의 각 Photo 공정 스텝. 제품당 30~60개 |
| **열(Column)** | 공정 조건 파라미터. 약 300개 |
| **카테고리 그룹** | 4개 그룹 (아래 참조) |

**카테고리 그룹 (Photo 공정 기준)**

| 카테고리 | 설명 | 대표 파라미터 예시 |
|----------|------|-------------------|
| **SP (Spin/PR)** | PR 도포, 스핀, 프리베이크, 접착제 등 코팅 관련 | PR_TYPE, SPIN_SPEED, PREBAKE_TEMP, ADHESION_USE 등 |
| **SC (Scanner/Expose)** | 노광 장비, 레티클, 에너지, 포커스, 정렬 등 노광 관련 | TOOL_ID, RETICLE_ID, EXPOSE_ENERGY, FOCUS, ILLUM_MODE 등 |
| **OVL (Overlay)** | 오버레이 측정, 보정, APC 등 정렬 정밀도 관련 | SPEC_X/Y, REF_LAYER, CORRECT_X/Y, APC_USE 등 |
| **DEV (Develop)** | 현상, 린스, 포스트베이크, CD 측정, 검사 등 후처리 | DEV_TYPE, PUDDLE_TIME, CD_TARGET, INSPECT_TOOL 등 |

```
| Layer        | SP_PR_TYPE | SP_SPIN1_SPEED | ... | SC_TOOL_ID | SC_ENERGY | ... | OVL_SPEC_X | ... | DEV_TYPE | ... |
|--------------|------------|----------------|-----|------------|-----------|-----|------------|-----|----------|-----|
| AA_PHOTO     | KrF-A01    | 1500           | ... | NSR-S322F  | 35.5      | ... | 8.5        | ... | NMD-3    | ... |
| GATE_PHOTO   | ArF-C01    | 2000           | ... | XT-1900Gi  | 42.0      | ... | 5.0        | ... | TMAH     | ... |
| ...          | ...        | ...            | ... | ...        | ...       | ... | ...        | ... | ...      | ... |
```

### 3.2 Backbone 관계

- 기존 양산 제품의 조건표가 backbone 역할
- 한 제품의 조건표는 **메인 backbone 1개** + **레이어별 개별 backbone 교체**로 구성
- 레이어 이름은 제품 간 동일하거나 매핑 가능
- 신규 레이어는 빈 행으로 추가 후 별도 backbone 선택 가능
- 각 레이어의 backbone 출처 정보는 시스템에 자동 기록

### 3.3 Recipe XML

- 설비에서 추출한 공정 조건 데이터 (USB/네트워크)
- Recipe XML 1개 = 레이어 1개의 조건에 해당
- XML 파라미터명과 조건표 컬럼명이 다르므로 **매핑 테이블** 필요

**Recipe XML 구조 예시**:
```xml
<?xml version="1.0" encoding="UTF-8"?>
<Recipe layer="AA_PHOTO" tool="NSR-S322F-01">
  <CoatModule>
    <ResistType>KrF-A01</ResistType>
    <DispenseVol>1.85</DispenseVol>
    <Spin1><Speed>1500</Speed><Time>5</Time></Spin1>
  </CoatModule>
  <BakeModule>
    <PreBake><Temp>110</Temp><Time>90</Time></PreBake>
  </BakeModule>
  <ExposeModule>
    <Energy>35.5</Energy>
    <Focus>0.025</Focus>
  </ExposeModule>
  <DevModule>
    <Chemical>NMD-3</Chemical>
    <PuddleTime>45</PuddleTime>
  </DevModule>
</Recipe>
```

**XML 매핑 테이블 예시**:

| XML XPath | 조건표 컬럼명 | 카테고리 | 데이터 타입 |
|-----------|--------------|----------|------------|
| /Recipe/CoatModule/ResistType | SP_PR_TYPE | SP | STRING |
| /Recipe/CoatModule/Spin1/Speed | SP_SPIN1_SPEED_rpm | SP | INT |
| /Recipe/BakeModule/PreBake/Temp | SP_PREBAKE_TEMP_C | SP | INT |
| /Recipe/ExposeModule/Energy | SC_EXPOSE_ENERGY_mJ | SC | FLOAT |
| /Recipe/DevModule/Chemical | DEV_TYPE | DEV | STRING |

## 4. 워크플로우

전체 프로세스는 5단계로 구성된다.

### Step 1. 프로젝트 생성 및 메인 Backbone 선택

**목적**: 신규 제품의 조건표 초안을 기존 제품 기반으로 빠르게 생성

**동작**:
1. 사용자가 신규 제품명을 입력
2. 메인 backbone 제품을 검색·선택
3. 선택된 backbone의 전체 조건표(모든 레이어, 모든 컬럼)가 복사되어 초안 생성
4. 프로젝트 상태: **Draft**

**UI 요소**:
- 제품명 입력 필드
- Backbone 제품 검색/선택 (자동완성 또는 드롭다운)
- 생성 버튼

### Step 2. 레이어별 Backbone 교체

**목적**: 특정 레이어에 다른 제품의 조건을 적용

**동작**:
1. 레이어 목록에서 교체가 필요한 레이어 선택
2. 해당 레이어에 적용할 다른 backbone 제품 선택
3. 선택된 backbone의 동일 레이어명(또는 매핑된 레이어)의 조건값으로 덮어쓰기
4. 어떤 레이어에 어떤 backbone을 적용했는지 **자동 기록**
5. 신규 레이어 추가: 빈 행 추가 → backbone 선택 → 값 가져오기

**UI 요소**:
- 레이어 목록 (각 레이어별 현재 backbone 출처 표시)
- Backbone 교체 버튼/드롭다운
- 신규 레이어 추가 버튼

### Step 3. Recipe 기반 최신화 (선택적)

**목적**: 설비의 실제 Recipe를 반영하여 조건표를 최신 상태로 갱신

**동작**:
1. 레이어별 Recipe XML 파일 업로드 (단일/다중 파일)
2. 매핑 테이블 기반으로 XML 파라미터를 조건표 컬럼에 매칭
3. 현재 조건표 값과 Recipe 값의 **diff(차이)를 표시**
4. 사용자가 항목별로 "적용" 또는 "무시" 선택 (일괄 적용도 가능)

**UI 요소**:
- 파일 업로드 영역 (드래그 앤 드롭)
- Diff 테이블: 컬럼명 | 현재값 | Recipe값 | 차이 | 적용 여부
- 전체 적용 / 전체 무시 버튼

### Step 4. 수동 편집 및 검증

**목적**: 세부 조건 수동 조정 및 데이터 무결성 확보

**동작**: 아래 "5. 편집 UI 상세 설계" 참조

### Step 5. 전산 입력용 테이블 출력

**목적**: 사내 전산 시스템에 복붙할 수 있는 포맷으로 데이터 변환·다운로드

**동작**:
1. 승인 완료된(Approved) 조건표에서 출력 가능
2. 대상 전산 시스템 선택 (또는 일괄 출력)
3. 해당 전산의 포맷(config)에 따라 테이블 자동 변환
4. Excel 파일로 다운로드 → 사용자가 전산에 복사·붙여넣기

상세 포맷 정의는 "7. 전산 시스템 출력 포맷" 참조.

### 5.2 핵심 UI 요소

**카테고리 탭**
- 상단에 SP / SC / OVL / DEV 탭 배치
- 탭 전환 시 해당 카테고리의 컬럼(60~100개)만 AG Grid에 표시
- 300개를 한 번에 보는 대신 카테고리 단위로 분할하여 인지 부하 감소

**AG Grid 스프레드시트**
- AG Grid Community Edition 사용
- Excel과 유사한 경험: 셀 클릭 → 즉시 편집, 복사·붙여넣기 지원
- 좌측 레이어명 컬럼 고정 (가로 스크롤 시에도 항상 표시, pinned column)
- 컬럼 필터/정렬 지원
- 셀 타입별 에디터: 숫자 입력, 드롭다운 선택, 텍스트 입력

**레이어 네비게이션 패널** (좌측)
- 전체 레이어 목록 표시
- 클릭 시 해당 레이어 행으로 자동 스크롤 (AG Grid API 연동)
- 각 레이어 옆에 오류 건수 뱃지 표시 (예: ⚠2)
- 현재 backbone 출처 표시

**셀 시각적 피드백** (AG Grid cellStyle 활용)
- 🔴 빨간 배경: 검증 오류 (범위 초과, 필수값 누락, 논리적 모순 등)
- 🟡 노란 배경: backbone 대비 변경된 값
- 🟢 초록 배경: Recipe XML에서 업데이트된 값
- 셀 호버 시 툴팁: "backbone 원래값: 450 → 현재: 500"

**하단 검증 패널**
- 전체 오류 목록을 리스트로 표시
- 각 오류 항목 클릭 시 해당 셀로 자동 이동 및 포커스
- 오류 유형별 필터링 가능

### 5.3 검증 체계

**검증 타이밍**
- **실시간 검증**: 셀 편집 완료(blur/onCellValueChanged) 시 해당 셀의 검증 규칙 즉시 실행 (프론트엔드)
- **전체 검증**: 저장 버튼 클릭 시 전체 조건표에 대한 종합 검증 실행 (백엔드)

**검증 규칙 유형**

| 유형 | 설명 | 예시 |
|------|------|------|
| 숫자 범위 | 컬럼별 min/max 값 범위 초과 여부 | SP_PREBAKE_TEMP이 음수 |
| 필수값 | 반드시 입력되어야 하는 컬럼 | SC_EXPOSE_ENERGY 누락 |
| 조건부 필수 | 특정 컬럼이 Y이면 연관 컬럼 필수 입력 | SP_ADHESION_USE=Y인데 SP_ADHESION_TYPE 누락 |
| 레이어 간 논리적 모순 | 레이어 간 관계에서의 모순 검출 | 후속 규칙 정의 필요 |
| Backbone 대비 변경 하이라이트 | backbone 원본값 대비 변경 사항 시각적 표시 | 변경된 셀을 노란색으로 표시 |

**저장 정책**

| 상태 | 오류 허용 여부 |
|------|---------------|
| Draft (편집 중) | 오류 있어도 저장 가능. 오류 건수 경고 표시 |
| Review 요청 (최종 완료) | 오류 0건이어야만 상태 전환 가능 |

## 6. 승인 프로세스

### 6.1 상태 흐름

```
Draft ──────────► Review ──────────► Approved
  ▲                  │                    │
  │                  ▼                    │
  └──────────── Rejected                 │
                                         ▼
                                    Export 가능
```

### 6.2 승인 규칙

- **승인 단위**: 전체 조건표를 한 번에 승인/반려 (부분 승인 없음)
- **승인 단계**: 편집자 → 검토자 (1단계)
- **Review 전환 조건**: 검증 오류 0건
- **반려**: 검토자가 특정 셀/레이어에 코멘트를 남기고 반려 → Draft로 복귀 → 편집자가 코멘트 위치로 바로 이동 가능

### 6.3 변경 이력 추적

- 모든 셀 변경에 대해 **누가, 언제, 무엇을(이전값 → 변경값)** 기록
- 변경 이력 조회 기능 (셀 단위 / 전체 타임라인)
- 상태 전환 이력 기록 (Draft → Review → Approved/Rejected)

## 7. 전산 시스템 출력 포맷

### 7.1 변환 엔진 구조

변환 로직(3가지 유형)은 코드로 구현하되, 각 전산 시스템별 세부 설정은 config(DB)로 관리한다. 새로운 전산 시스템 추가 시 config만 추가하면 대응 가능하며, 새로운 **유형**이 필요할 때만 코드 개발이 필요하다.

### 7.2 변환 유형 정의

**Type A — 1행 1레이어 (가로형)**

원본 조건표와 유사한 구조. 지정된 컬럼만 추출하고 컬럼명을 전산 시스템명으로 변환.

```
| LAYER_ID   | PRODUCT_ID | RESIST_CODE | COAT_SPEED1 | PAB_TEMP | ... |
|------------|------------|-------------|-------------|----------|-----|
| AA_PHOTO   | PROD-2025A | KrF-A01     | 1500        | 110      | ... |
| GATE_PHOTO | PROD-2025A | ArF-C01     | 2000        | 120      | ... |
```

**Type B — 설비구분 다행**

같은 레이어가 사용 가능한 설비별로 여러 행으로 분리. 설비별로 일부 파라미터(에너지, 포커스 등)가 다를 수 있음.

```
| LAYER_ID   | PRODUCT_ID | EQUIP_ID      | RETICLE         | ENERGY | FOCUS  | ... |
|------------|------------|---------------|-----------------|--------|--------|-----|
| AA_PHOTO   | PROD-2025A | NSR-S322F-01  | RTL-AA-001      | 35.5   | 0.025  | ... |
| AA_PHOTO   | PROD-2025A | NSR-S322F-02  | RTL-AA-001      | 33.8   | 0.021  | ... |
| AA_PHOTO   | PROD-2025A | NSR-S631E-01  | RTL-AA-001      | 36.2   | 0.028  | ... |
| GATE_PHOTO | PROD-2025A | XT-1900Gi-01  | RTL-GATE-001    | 42.0   | -0.010 | ... |
```

**Type C — 키-밸류 (세로 전치)**

컬럼이 행으로 전치된 형태. 각 파라미터가 KEY-VALUE 쌍으로 표현됨.

```
| LAYER_ID   | PRODUCT_ID | PARAM_KEY | PARAM_VALUE | UNIT  |
|------------|------------|-----------|-------------|-------|
| AA_PHOTO   | PROD-2025A | SPEC_X    | 8.5         | nm    |
| AA_PHOTO   | PROD-2025A | SPEC_Y    | 7.2         | nm    |
| AA_PHOTO   | PROD-2025A | REF_LAYER | WAFER_EDGE  |       |
| AA_PHOTO   | PROD-2025A | TOOL      | ARCHER-500  |       |
| AA_PHOTO   | PROD-2025A | CORR_X    | 2.15        | nm    |
```

### 7.3 전산 시스템 목록

| # | 시스템명 | 포맷 유형 | 포함 카테고리 | 상태 |
|---|---------|----------|-------------|------|
| 1 | MES-TRACK | Type A | SP + DEV | 포맷 정의 완료 |
| 2 | EQP-SCANNER | Type B | SC | 포맷 정의 완료 |
| 3 | SPC-OVL | Type C | OVL | 포맷 정의 완료 |
| 4 | MES-COATER | Type A | SP | 포맷 미정 |
| 5 | MES-DEV | Type A | DEV | 포맷 미정 |
| 6 | SPC-CD | Type C | DEV (CD관련) | 포맷 미정 |
| 7 | EQP-RETICLE | Type A | SC (레티클관련) | 포맷 미정 |
| 8 | APC-SYSTEM | Type C | OVL + SC | 포맷 미정 |
| 9 | YIELD-DB | Type A | 전체 | 포맷 미정 |
| 10 | REPORT-GEN | Type A | 전체 | 포맷 미정 |

### 7.4 전산별 Config 구조

각 전산 시스템에 대해 다음을 DB에 저장:

```
{
  "system_name": "MES-TRACK",
  "format_type": "TYPE_A",
  "description": "트랙 장비 제어용",
  "column_mappings": [
    {
      "source_column": "SP_PR_TYPE",
      "target_column": "RESIST_CODE",
      "required": true
    },
    {
      "source_column": "SP_SPIN1_SPEED_rpm",
      "target_column": "COAT_SPEED1",
      "required": true
    },
    ...
  ],
  "additional_options": {
    // Type B인 경우: 설비 배정 정보 소스
    // Type C인 경우: UNIT 매핑 등
  }
}
```

## 8. 관리자 설정

### 8.1 Recipe XML ↔ 조건표 컬럼 매핑

- XML XPath와 조건표 컬럼명의 매핑 관계를 정의
- 매핑 추가/수정/삭제 기능
- 데이터 타입 지정 (STRING, INT, FLOAT, Y/N)

### 8.2 컬럼별 검증 규칙 설정

- 각 컬럼에 대해 적용할 검증 규칙을 설정
- 설정 가능한 항목:
  - 데이터 타입 (숫자, 문자, 선택값 등)
  - 숫자 범위 (min, max)
  - 필수 여부
  - 조건부 필수 규칙 (예: "SP_ADHESION_USE가 Y이면 SP_ADHESION_TYPE, SP_ADHESION_TEMP 필수")
- 검증 규칙 일괄 편집 (Excel 업로드로 대량 설정 가능)

### 8.3 카테고리 그룹핑 정의

- 약 300개 컬럼을 4개 카테고리 그룹(SP/SC/OVL/DEV)으로 분류하는 설정
- 각 그룹에 포함되는 컬럼 목록 관리
- 그룹 순서(탭 순서) 설정

### 8.4 전산 시스템 출력 포맷 설정

- 전산 시스템 추가/수정/삭제
- 변환 유형 선택 (Type A / B / C)
- 컬럼 매핑 설정 (조건표 컬럼명 → 전산 컬럼명, 필수 여부, 순서)
- Type B 추가 설정: 설비 배정 정보
- Type C 추가 설정: UNIT 매핑

### 8.5 사용자/권한 관리

- 사용자 목록 관리 (추가/수정/삭제)
- 역할 지정 (편집자 / 검토자 / 관리자)
- 인증 방식: 미정

## 9. 개발 단계 제안

점진적으로 가치를 전달하기 위해 다음과 같은 개발 단계를 제안한다.

### Phase 1: 핵심 편집 기능 (MVP)

**목표**: "300개 컬럼을 웹에서 편집할 수 있다"는 핵심 가치 증명

- 프로젝트 생성 + 메인 backbone 선택 (Step 1)
- 카테고리 탭 기반 AG Grid 편집 UI (Step 4 핵심)
- 기본 검증: 숫자 범위, 필수값
- Backbone 대비 변경 하이라이트
- 저장/불러오기
- Docker Compose 기반 개발 환경 구축

**기술 산출물**: React + FastAPI + PostgreSQL 기본 구조, AG Grid 통합

### Phase 2: 데이터 입력 자동화

**목표**: 수작업 데이터 입력을 최소화

- 레이어별 backbone 교체 (Step 2)
- Recipe XML 업로드 + 파싱 + diff 적용 (Step 3)
- 관리자 설정: XML 매핑, 검증 규칙, 카테고리 그룹핑

### Phase 3: 워크플로우 및 출력

**목표**: 업무 프로세스 전체를 시스템화

- 승인 프로세스 (Draft → Review → Approved/Rejected)
- 변경 이력 추적
- 코멘트 기능 (반려 시)
- 전산 입력용 테이블 출력 (Step 5) — 주요 3개 전산 먼저

### Phase 4: 고도화

**목표**: 전체 커버리지 및 운영 안정화

- 고급 검증 (레이어 간 논리적 모순, 조건부 필수)
- 전산 출력 포맷 확장 (10개 시스템 config 완성)
- 사용자/권한 관리 고도화
- 운영 편의 기능 (대시보드, 통계 등)
